# Conventions for a standalone native SDK doc tree

Written while documenting `enriched-markdown-android`. Follow it to give
`enriched-markdown-ios` the same shape. Not a published page - keep it out of
`docs/docs/`.

## 1. The reader

**A native developer who may know nothing about React Native, and never needs
to.** This is the rule everything else follows from:

- Never explain a feature by comparison to the RN package. No "unlike React
  Native…", no "the RN prop is called…".
- **No "not available on <platform>" tables.** A list of RN props the reader
  can't use is a list of things they now have to learn about to dismiss. If a
  capability is missing, either say so where the reader would look for it, or
  leave it out and let the roadmap carry it.
- **Zero RN mentions. No exceptions.** Not even the reassurance that it isn't
  needed ("you do not need React Native installed to use it") - naming it is
  what teaches the reader it exists. Same for oblique versions: "shared with the
  other platforms", "has no counterpart here", "across all platforms". State the
  fact on its own terms (a palette is "GitHub's palette", full stop) or cut it.
- Missing capabilities are described by **what the reader can't do**, never by
  which package has it. The editor section says this package renders and does
  not edit, and points at the roadmap - it does not name the component that
  ships elsewhere.
- Cross-platform pages (`rich-text-formatting/`, `user-experience/`, `misc/`)
  stay shared; link into them freely.

## 2. Shape

Mirror `docs/react-native/`:

```
<platform>/            basics/        (10)  installation, your-first-screen
                       api-reference/ (20)  <Component>, <Theme>, style-properties,
                                            element-structure
                       guides/        (30)  …platform-specific
```

Order comes from `_category_.json` `position` per folder and `sidebar_position`
in each page's frontmatter. The tree is autogenerated - never edit `sidebars.js`.

**Don't force parity where the platform differs.** Add pages the platform needs
(Android got `markdown-theme.md` for `MarkdownTheme`/`markdownStyle`, which has
no RN counterpart), and drop pages it doesn't:

- **No editor page.** `EnrichedMarkdownTextInput` is RN-only. One short
  "Editor on <platform>" section on `your-first-screen`, framed as *not
  available yet*, linking `/misc/roadmap#the-editor-on-native`.
- **No testing guide** unless the platform genuinely has a consumer story. On
  Android there was none: the parser is a JNI `.so`, its own tests are
  instrumented, renderer tests hand-build ASTs through an unpublished factory,
  and nothing importable ships. Better to omit a page than to invent one. Check
  the iOS equivalent before assuming either way.

## 3. Verify everything against source

The single biggest source of value, and of errors.

- **Read the code, not the package README.** Android's README disagreed with
  the code twice (a style property that isn't exposed; a property renamed in
  the public DSL).
- **Defaults come from the defaults file**, transcribed - not remembered.
- **Check that a flag has a renderer**, not just a parser. Android parses
  `highlight` and `latexMath` and draws neither, and the fallback renderer emits
  only a node's own text - so enabling them *deletes the content* instead of
  showing it unstyled. That is a `:::danger`, not a footnote. Confirm the
  equivalent iOS fallback before repeating the claim.
- When something is WIP, say what actually happens today, not what it will do.
- `truth_docs.csv` is the starting map, not the evidence. It's per-row and
  sometimes phrased for RN; confirm each row you rely on in the platform's code.

## 4. Page conventions

- **Types go inline next to the parameter they belong to**, not in a `## Types`
  section at the bottom: the `PropInfo` line, then the `data class` /`struct`
  block right under it if it needs one.
- `<PropInfo type="…" default="…" />` (or `required`) under **every** parameter,
  after the prose. Registered globally, usable in `.md`.
- One `###` per parameter; `####` for sub-fields of an options object.
- Use an explicit `{#anchor}` on any heading you link to whose text may change.
- Admonition style: `:::note` for a caveat, `:::caution` for a sharp edge,
  `:::danger` only for data loss or a broken build.
- Prose voice: say what a thing *is for* and what it *costs*, then show the
  smallest snippet that proves it. Lead a section with the consequence, not the
  mechanism.
- Every code block is copy-pasteable and compiles in principle - real imports,
  real types, no pseudo-code.

## 5. Guides earn their place

A guide exists because something is **non-obvious and costs the reader a bug**.
Ask what breaks without it. The Android four:

| Guide | Exists because |
| --- | --- |
| Parser extensions | Flags change *parsing*, and two of them delete content |
| Images and caching | Far more URL schemes work than you'd guess; caches are invisible |
| Custom fonts | A multi-file `FontFamily` silently collapses to one file |
| Compose interop | View recycling resets in-view state; nothing renders in previews |

Keep `your-first-screen` **narrow** - it gets a reader from empty project to
rendered Markdown and hands off. If a topic wants its own section there, it
belongs in a guide instead.

## 6. Gates

Both must pass before handing a task back:

```sh
yarn build           # onBrokenLinks + onBrokenAnchors are 'throw'
yarn check-examples  # src/examples must stay 1:1 with docs
```

A passing build is real verification that every cross-page link **and anchor**
resolves. Native trees have no runnable web examples today, so `check-examples`
only needs to stay green - but if iOS ever gets examples they must live at
`src/examples/ios/<doc path>/<Name>.tsx`.

Also update, in the same pass: `docs/CLAUDE.md`'s section map, the
`/misc/compatibility` platform section, and the platform bullet on
`introduction/getting-started.mdx` (it currently says iOS docs are "coming
soon").

## 7. Process that worked

Four tasks, each ending in review before the next starts:

1. **Scaffold** - full tree, frontmatter, every heading, `PropInfo` with real
   types/defaults, `<!-- TODO -->` notes, no prose. Cheapest point to argue
   about shape.
2. **Basics** - installation + first screen.
3. **API reference** - the component, theming, style properties, element
   structure.
4. **Guides.**

Keep a WIP `:::caution` on every unfinished page and remove them only when told.
